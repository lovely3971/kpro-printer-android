KANAKKU PULLA PRO ANDROID — FINAL FIXED V5
============================================

ROOT CAUSE (confirmed by code tracing, not assumption):

The app's billing screen (Bill list, Bill Print, Barcode/Label Print,
Add Product, etc.) is NOT part of the top-level index.html page.
It lives inside <template id="kpBillingTemplate"> and is only
activated when its HTML is copied into a separate <iframe
id="billingAppFrame"> using `iframe.srcdoc = template.innerHTML`.

An <iframe> has its own independent JavaScript "window" — code
defined in the parent page CANNOT be seen or reached by code/buttons
running inside that iframe, and vice versa.

The entire "force native Android Bluetooth" layer — the
kpNativeAndroidPrinterBridgeV2 override script, the whole
Bluetooth engine (KP_BT_SERVICES, kpBtConnect, kpBtWrite,
kpBtDisconnect, kpBtDirectSupported, kpBtSetStatus, kpMobileBluetoothPrintBill,
kpMobileBluetoothPrintSelectedLabels, kpMobileBluetoothPrintBulkLabels,
kpPrintLabelJobs, kpRenderLabelCanvas, TSPL/ESC-POS bitmap builders),
and the entire Barcode/Label print modal (kpBarcodePrintFlow +
kpOpenBarcodePrintFlowUI / kpChooseBarcodePrintSizeUI /
kpConfirmBarcodePrintUI) — was sitting in the TOP-LEVEL document,
AFTER </template>.

But every Bill Print button, every Barcode/Label Print button, and
the original browser-popup print functions (printBarcodeLabels,
printBulkBarcodeLabels, printLabelHtml, kpUseBillShareHandoff,
kpIsIPhoneLike) all live INSIDE the iframe (inside
kpBillingTemplate).

Result on a real Android phone:
- Bill Print: inside the iframe, kpUseBillShareHandoff() always
  evaluates `!navigator.bluetooth` (Web Bluetooth is not available
  in a plain Android WebView) as true, so it is always treated as
  "iPhone-like" and always took the Share Bill -> Share Sheet ->
  Open Label path — on Android too. The top-level override that
  was supposed to force this to false never reached the iframe.
- Barcode/Label Print: the "Bluetooth Label Print" / "Bluetooth
  Print All" buttons call kpOpenBarcodePrintFlowUI(), which did not
  exist at all inside the iframe (it only existed at top level) —
  clicking them silently failed. The plain "Print Labels" / "Print
  All Labels" buttons called the iframe's own original functions,
  which still used window.open('','_blank') — a plain WebView has
  no popup-window support, so Android's WebViewClient handed that
  navigation to the phone's default browser (this is the blank
  screen -> Chrome tab seen in the test video).

FIX APPLIED (surgical relocation only — nothing rewritten):

The block from <style id="kpMobileBluetoothStyles"> through the end
of <script id="kpNativeAndroidPrinterBridgeV2"> (380 lines: the
Bluetooth engine, the Mobile Printer FAB/modal, the Barcode/Label
print modal + its controller functions, and the native-bridge
override) was moved, byte-for-byte, from the top-level document to
just before the closing </body> INSIDE <template id="kpBillingTemplate">.

No line was added, removed, or edited — verified by sorting and
diffing the full file content before and after the move (identical).

This puts the override script in the SAME JavaScript window as the
Bill/Barcode buttons it needs to control, so:

V6 UPDATE — from real BT-58L / PeriPeri test photos
============================================

Issue 1 — Barcode/Label print came out upside-down (180° rotated),
and printer showed "Shift to Label mode" on its own:
- Root cause: the TSPL label commands (kpTsplBitmap, used for every
  real label print, and kpBtTestLabel, the Test Label button) sent
  `DIRECTION 1`, which prints the label rotated 180°.
- Fix: changed `DIRECTION 1` -> `DIRECTION 0` in both places.
- "Shift to Label mode" text is printed by the printer's own
  firmware, not by this app (searched the whole project — no such
  string exists anywhere in our code). That message is the PeriPeri
  device auto-detecting/announcing its mode; nothing to change on
  the app side for that specific text.
- Not verified on real hardware yet — needs a new Test Label /
  real label print to confirm orientation is now correct.

Issue 2 — Bill print (80mm) came out with the right-hand side of
every row clipped (RATE/AMOUNT columns cut short, totals missing):
- Root cause: kpMobileBluetoothPrintBill was running html2canvas
  directly on the on-screen #billActionPaper preview element. That
  element sits inside a modal that can be horizontally scrolled/
  zoomed on a phone screen; html2canvas can capture only the
  currently visible/laid-out box in that situation, cutting off
  whatever was scrolled out of view — even though the on-screen
  "Print Preview" step (a plain screenshot-free HTML view) still
  showed the full content correctly.
- Fix: before capturing, the bill paper's HTML is now cloned into a
  fresh, off-screen container (position:fixed, far off the left
  edge, not display:none) with its width explicitly fixed to the
  chosen paper size (58mm/80mm) and no scroll/zoom/transform
  applied — the exact same off-screen-clone technique already used
  successfully for label printing (kpRenderLabelCanvas). html2canvas
  then captures that clean, full-width clone instead of the
  on-screen modal. The temporary clone is removed right after.
- Not verified on real hardware yet — needs a new bill print to
  confirm every column and the total line print in full.

FILES CHANGED (V6): app/src/main/assets/www/index.html only —
2 lines changed (DIRECTION 1->0, twice) + kpMobileBluetoothPrintBill
capture logic rewritten to use an off-screen clone. No other file
touched, no UI/design changed.

V7 UPDATE — Share button, Address field, Label colors, Fixed signing key
============================================

Issue 3 — Barcode/Label print came out with a dark/green background
and white text instead of a plain white-background/black-text label:
- Root cause: the app already has CSS that forces white background +
  black text for barcode labels, but only inside two specific on-
  screen containers (#page-barcodes and #labelPreviewArea). The
  Bluetooth print path (kpRenderLabelCanvas) renders each label into
  its own throwaway off-screen <div> that has neither of those IDs,
  so the label inherited the app's dark theme text colour instead.
- Fix: kpRenderLabelCanvas now injects a small inline <style> into
  that same off-screen div forcing white background / black text on
  the label and every element inside it, before the screenshot is
  taken for the printer. Nothing on the on-screen Barcode Design
  page or Live Preview panel was touched.
- Not verified on real hardware yet.

Issue 4 — "Share PDF / Files" button did nothing:
- Root cause: a plain Android WebView has neither the Web Share API
  (navigator.share) nor a way to catch a blob: download click — so
  the old code's two fallbacks were both silently no-ops on Android.
- Fix (new native capability, mirrors how Bluetooth print was fixed):
  - MainActivity.java: PrinterBridge gained a shareFile(base64,
    filename, mime) method that writes the file to the app's cache,
    gets a content:// URI via a new FileProvider, and opens Android's
    normal Share sheet (WhatsApp, Files, Drive, etc.).
  - AndroidManifest.xml: added the FileProvider <provider> entry.
  - New file app/src/main/res/xml/file_paths.xml: FileProvider path
    config (exposes only the app's own "shared" cache folder).
  - app/build.gradle: added the androidx.core:core library (needed
    for FileProvider) — the only new dependency in the project.
  - index.html: shareCurrentBillFile() now calls
    window.KPRO_NATIVE.shareFile(...) first when available; the old
    navigator.share / download-link code is kept as a fallback for
    non-Android contexts, unchanged.
- Not verified on real hardware yet.

Issue 5 — Shop Profile "Full Address" was a single-line box:
- Fix: changed the #setShopAddress field from <input> to a 3-row
  <textarea> (multi-line), so owners can type address across several
  lines. Reads/saves exactly like before (.value works the same way
  on a textarea) — no other Shop Profile logic touched.

Issue 6 — App had to be uninstalled before every new build could be
installed:
- Root cause: app/build.gradle had no signingConfig, so Gradle's
  default debug signing auto-generates a new random debug keystore
  on whichever machine builds it. Since GitHub Actions gives a fresh
  machine every run, every APK from every workflow run was signed
  with a different key — Android refuses to install a new APK over
  an existing app unless the signing key matches, so every previous
  version needed a manual uninstall first.
- Fix: generated one permanent keystore
  (app/kanakku-debug.keystore, committed to the repo) and pointed
  app/build.gradle's debug signingConfig at it explicitly. Every
  future build from this project will be signed with this same key,
  so installing a new APK over an older one (from V7 onwards) will
  update in place — no more uninstalling first.
- This only takes effect from this build onward: V7 itself still
  needs one manual uninstall of whatever is currently installed
  (since it's signed with a different, older random key). Every
  build after V7 will update in place automatically.

V7 UPDATE #2 — Barcode scanner camera + louder beep
(added before V7 was ever installed, so still shipped as V7)
============================================

Issue 7 — "Scan a product" camera stuck on "Starting camera...":
- Root cause: the scanner uses the browser's own camera API
  (getUserMedia) via the Html5Qrcode library. WebChromeClient's
  onPermissionRequest was unconditionally granting the *web* camera
  permission, but the underlying Android OS camera permission
  (android.permission.CAMERA) was never actually requested from the
  user at runtime — it was only declared in the Manifest. Without
  the real OS-level grant, the browser-layer camera request has
  nothing to open, so the camera preview never starts and the
  scanner sits on "Starting camera..." forever.
- Fix: onPermissionRequest now checks whether the OS camera
  permission is already granted; if not, it requests it from the
  user first (standard Android permission dialog) and only grants
  the web request once that resolves. This is the same "OS
  permission + web permission" pattern already used for Bluetooth
  and location in this app.
- Not verified on real hardware yet — needs the Android camera
  permission popup to appear the first time "Scan a product" (or the
  camera icon in Add Product) is opened, and Allow to be tapped.

Issue 8 — Scan beep was too quiet:
- scannerSuccessBeep() already existed and was already wired to fire
  on every successful match; it just had very low volume (16%) and
  a very short, soft sine tone.
- Fix: increased volume to 90%, changed to a sharper square wave,
  and lengthened it slightly (90ms -> 160ms) so it's clearly audible
  like a real barcode-scanner beep. Nothing else about scanning
  behaviour changed.

FILES CHANGED (this update): index.html (scannerSuccessBeep only),
MainActivity.java (onPermissionRequest + onRequestPermissionsResult
updated to request the real Android CAMERA permission).
